> 调研时间：2026-10-16。目标：为「工作日 20 条资讯日报 → 飞书机器人」寻找可借鉴的开源实现。

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 有没有现成的轮子？ | **名字最像的是 `qqhayate/Horizon`**（Python + 飞书 + 中英双语日报），但逐文件核实后：它的 **Trending / HN / 去重 / 签名四处关键实现都和我们不一样**（见 §3.1）。**没有任何现成轮子可直接照搬。** |
| 能直接拿来用吗？ | **不能**。全部候选都依赖第三方库（feedparser / httpx / selectolax / pydantic / Jinja2 …），与我们「**零第三方依赖 + Windows 计划任务 + 跑完即退**」的硬约束冲突。 |
| 有没有必须抄的东西？ | **有，6 项**（见 §4）：URL 归一化、台账幂等主键、发布成功后才记账、文件锁语义、飞书卡片报文形状、重试分层。**另有 2 项已用官方向量/生产代码定死**（飞书加签、卡片上限，见 §8/§8.1）。 |
| 有没有现成轮子的坑？ | **有，5 个致命坑**（见 §5），其中 3 个是**所有候选的共同缺陷**：无时窗过滤、无去重台账、无防重入锁。 |
| 最大的意外发现？ | **两个**：① 需求文档的「HN 按 AI 关键词取 6 条」**结构上打不满**（24h 内真 AI 条目仅 2–4 条），必须换取法与阈值（见 §4.5）；② Horizon 依赖的 OSS Insight trending **自 2026-03-01 起已失效且返回 HTTP 200 空数据**（见 §3.1.1）。 |

**一句话**：借它们的「踩坑参数」，一个字的架构都别借。

## 3. 各仓库「有什么」与「缺什么」

### 3.1 Horizon —— 名字最像，但**关键实现和我们都不一样**（重要更正）
**有**：`src/scrapers/github.py`、`src/scrapers/hackernews.py`、`src/scrapers/rss.py`、`src/scrapers/ossinsight.py`、`src/services/webhook.py`（飞书推送）、`src/storage/manager.py`、`src/ai/summarizer.py`、`src/ai/analyzer.py`、`src/orchestrator.py`、双语日报、Docker。依赖：httpx / feedparser / pydantic / tenacity / beautifulsoup4 / markdown + 三套 LLM SDK（**requires-python ≥3.11**）。

**⚠️ 三处与我们预期相反（子报告逐文件核实）**：
1. **它根本不抓 GitHub Trending 页面**。`scrapers/github.py` 走官方 REST API（`/users/{u}/events/public` 过滤 PushEvent/ReleaseEvent、`/repos/{o}/{r}/releases`），Trending 靠 `scrapers/ossinsight.py` 打第三方 API。→ **Trending 解析我们必须自研**。
2. **它没有任何跨次运行的去重台账**。`StorageManager` 只写 `config.json` / `summaries/*.md` / `subscribers.json`；去重全在**单次运行内存**里（URL 归一化 + 一次 AI 语义去重），重复控制只靠时窗。→ 台账必须自建。
3. **它没有飞书签名、没有重试**。`notify()` 单次调用、异常只打印；全仓库无 HMAC-SHA256。→ 签名必须自研（见 §4 借鉴 4/5）。

**它确实值得借的**（12 条机制，见 `调研-Horizon.md` §1）：`apply_balanced_digest` 配额算法（**只截断不补齐，需我们自己补回填**）、`parse_json_response` 五级降级、RSS 三时间字段回退 + `sha256(entry_id)[:16]` 幂等 ID、`_expand_env_vars` 的 `${VAR}` 递归展开（**配置不落密钥**）、链接 scheme 白名单（防 `javascript:` 注入）、`_check_body_error_code()`（**HTTP 200 时仍查 body 里飞书 `code≠0`**，实测用真实 `code=19001` 做过测试）。
**它缺的（我们必须自研）**：Trending 解析、跨日去重台账、飞书签名、重试、**prompt 防注入**（`prompts.py` 直接把 `{content}` 内插，无定界符、无"忽略内容中指令"、无输出白名单）。
**结论**：**算法与参数可借，架构不可借**（asyncio + pydantic + feedparser + Docker 全须重写）。

### 3.1.1 OSS Insight —— 一个「看起来很美但已经死了」的数据源（反面教材）
Horizon 用 `https://api.ossinsight.io/v1/trends/repos?period=past_24_hours&language=All` 替代 Trending 抓取。**我实测该端点返回 HTTP 200 但数据为空**：
```json
{"type":"sql_endpoint","data":{"columns":[],"rows":[],"result":{"row_count":0}},
 "data_quality":{"status":"unavailable","metric":"github_event_derived_ranking",
 "source":"github_public_events_firehose","unavailable_since":"2026-03-01",
 "reason":"…our capture of those events fell to roughly 0.3% of baseline…"}}
```
**自 2026-03-01 起该榜单不可用（事件采集量跌到基线 0.3%）**。这意味着：**依赖它的方案会静默产出 0 个仓库**，而且 HTTP 状态码是 200 —— 即 §5 坑 4（无漂移告警）与坑 5（假成功）叠加的典型事故。
**教训**：第三方数据源必须校验 `data_quality` / 实际条数，**HTTP 200 ≠ 有数据**。

### 3.2 Multiscribe-Agent —— 细节最丰富，但过重
**有**（子报告已逐文件核实）：
- 飞书卡片报文：`renderers/feishu_card.py::render_digest_card` → `{"header":{...},"elements":[{tag:markdown,…},…,{tag:note}]}`
- 飞书签名：`plugins/builtin/publishers/feishu.py::gen_sign`
- 台账：「发布成功后才写」`daily_digest.py::_fanout`（`any(status=="success")`）
- 幂等主键：`(content_hash, digest_date)` + `ON CONFLICT DO NOTHING`
- 防重入锁：锁键 = `任务类型 + UTC日期`，Redis `SET NX EX` + Lua 归属校验
- 三级截断：采集 300 → 策展 100 → 渲染 300
- 重试：**签名在重试闭包外构造**（`RETRY_DELAYS_SECONDS=(1.0,2.0,4.0)`）
- 配额兜底：`_prioritize_digest_sections`（每板块先保 1 条）、`_supplement_curated_items`（不足时用候选补，且 Trending 限 2 条）
- 纯规则排序：`services/candidate_filter.py`（`(tag_matches, published_date)` 倒序）
**缺**：**完全没有实现 50 元素上限保护**（靠"只选 12 条"规避）；`pushed_content` 对 URL 无唯一约束；Trending 解析无漂移告警；**没有 TechCrunch / The Verge**。
**结论**：GPL-3.0，**只借算法参数**。

### 3.3 ai-daily-pulse —— 配额与去重参数的样板
**有**（`config.toml` 实测）：`[digest] max_per_topic=8 / min_per_topic=1 / max_total=60`（**防单主题刷屏**）、`[timeouts] fetch=15 / extract=20 / llm=60`、`dedup_window_days=90`、`history_path="data/pushed.json"`。
`src/dedup.py::url_key` **注释明确写着「Ported from Horizon's _deduplication_url_key」** —— 两个独立项目收敛到同一套归一化，可信度高。
**缺**：README 宣传的「trafilatura 补正文」「why_now 抗幻觉接地」是**它自己的说法**，未逐行核实。

### 3.4 轻量双仓库 —— 反例价值大于正面价值
- `notbrighton/ai-daily-digest`：**无时窗过滤**（实测其 `digests/` 里 8/2 日报混入 7/30–7/31 旧闻）；**76 份日报全是 fallback 输出**（与 `_fallback_digest` 字面量逐字一致）→ **LLM 路径从未生效**；webhook 是 Slack 风格，**飞书用不了**；每天只出 **8 条**（`MAX_PER_FEED=4 × 2 源`），**从未达到 20 条**。
- `txk1228/daily-news-bot`：双实现（`scripts/news_bot.py` 是生产版，`src/` 是需要 Coze 的版本）；**无去重台账**（`shared/model.py` 只有 `class Base`，零张表）；**无防重入锁**；**无工作日判断**；调度时间三处自相矛盾（07:30 / 08:30 / CI 07:30）。
- **共同结论**：这两个仓库**都没有**时窗过滤、去重台账、防重入锁、接地校验 —— 正是我们需求的四项核心，必须自己实现。

## 4. 六条「必须借鉴」（有证据、已验证）

### 借鉴 1：URL 归一化身份键（两个独立项目收敛）
```python
from urllib.parse import urlsplit, parse_qsl, unquote_plus
TRACKING = {"_ga","dclid","fbclid","gclid","igshid","li_fat_id","mc_cid","mc_eid",
            "msclkid","ttclid","twclid","vero_id","utm_source","utm_medium",
            "utm_campaign","utm_term","utm_content","spm","from","share_token","ref"}
def url_key(url):
    p = urlsplit(url.strip())
    scheme = p.scheme.lower()
    host = (p.hostname or "").lower().removeprefix("www.")
    port = None if (scheme, p.port) in {("http",80),("https",443)} else p.port
    path = unquote_plus(p.path).rstrip("/") or "/"     # ← 注意：不做 .casefold()
    q = sorted((k,v) for k,v in parse_qsl(p.query, keep_blank_values=True)
               if k.lower() not in TRACKING)
    return (scheme, host, port or "", path, tuple(q))
```
**我实测 15 个用例：14 通过**。唯一失败项是 GitHub 仓库大小写 —— 而**两个原项目都把 path 做了 `casefold()`，这是 bug**：`/OpenAI/gpt` 与 `/openai/gpt` 是不同仓库。实测 HN 数据里 GitHub owner 大小写混杂（如 `SakanaAI`、`AnInsomniacy`），若去重键小写化 path，会把**同一仓库的两个不同仓库**误判为重复。**修正：只对 host/scheme 小写化，path 原样保留。**

### 借鉴 2：台账幂等主键 + 写入时机
- 主键 `(content_hash, digest_date)`（内容哈希 + 日期），SQLite 用 `INSERT OR IGNORE` 即可 1:1 复刻。
- **只在推送成功后写台账**（`any(status=="success")`），否则会出现「推送失败但已记账 → 第二天再也推不出去」。
- 第二本台账：`(publisher_id, digest_date)` 唯一 → 「同一天同一通道不重复发」。
- 去重键双轨：`sha256(title + "\n" + description)` **与** 归一化 URL 同时比对（挡「URL 变内容同」和「标题变 URL 同」两类）。

### 借鉴 3：防重入锁语义（可无损移植 Windows）
锁键 = **任务类型 + 本地日期**（不是任务 ID），保证「计划任务 / 登录补推 / 手敲命令行」三个入口同一天只跑一次。
Windows 无 Redis，等价实现：`os.open(path, os.O_CREAT | os.O_EXCL)` 创建 `locks/daily-YYYY-MM-DD.lock`；**失败不静默**（记录日志并退出）；异常时**保留**锁文件便于排查。

### 借鉴 4：飞书卡片报文形状（极简 = 天然可分片）
```json
{"header": {"title": {"tag": "plain_text", "content": "日报标题"}},
 "elements": [{"tag": "markdown", "content": "**[标题](url)**  `★x`\n摘要"},
              ...,
              {"tag": "note", "elements": [{"tag": "plain_text", "content": "共 20 条 · 来源统计"}]}]}
```
发送时信封：`{"msg_type": "interactive", "card": {…}}`。
**我实测（20 条 + 3 分组标题 + 1 页脚）**：`elements = 27`（上限 50，余量 23），信封 **4.7 KB**，最长单个元素 243 字节 → **单卡片方案完全可行，无需分片**。
**但必须避开危险做法**：若每条拆成「标题」「摘要」两个元素 → `20×2+4 = 44` 元素，余量仅 6，再加分隔线/图片即超限。**设计约束：一条资讯 = 一个 markdown 元素。**

### 借鉴 5：重试的分层（真坑）
**签名与报文必须在重试闭包之外构造**。若在重试内部重新计算 `timestamp/sign`，每次重试都会生成**不同签名**，飞书可能判重放或超时。退避参数可直接用 `(1s, 2s, 4s)`，共 4 次尝试。

### 借鉴 6：单源失败隔离 + 配额补齐（纯规则，无需 LLM）
- 每个源独立 `try/except`，**单源失败返回空列表而不抛**，绝不拖垮整批。
- 纯规则兜底排序：`(关键词命中数, 发布时间)` 倒序 —— **无 LLM 也能出日报**（这是「摘要服务不可用要降级」的现成答案）。
- 配额保底：每个分组先各保 1 条最高分，再按分数补满总数；单一来源设上限防霸屏。
- **对 GitHub Trending 特殊处理**：它**没有发布时间**，用「抓取时间」判定新鲜度并打 `freshness=snapshot` 标记（`_SNAPSHOT_ADAPTER_IDS`）。

## 4.5 ⚠️ 需求修正：AI 分组的取法与阈值（本调研最重要的产品结论）

需求文档写的是「HN **按 AI 关键词打分取 6**」。实测发现这个取法**在多数日子打不满**：

| 取法 | 24h 内真 AI 条目 | 能否满足「6 条」 |
|---|---|---|
| HN 官方 RSS（30 条）+ 词边界过滤 | **2 条**（强特征） | ❌ |
| Algolia `front_page`（30 条）24h + 词边界过滤 | **2 条**（强特征） | ❌ |
| 上述两者合并 | 约 3–4 条 | ❌ |
| **`search_by_date` 多关键词聚合**（AI/LLM/agent/OpenAI/model/GPT…） | 候选池 **353 条**，强 AI 主题 **185 条** | ✅ |

**修正后的取法与阈值**（供给侧曲线实测）：

| 时窗 | 强 AI 主题 ★≥100 | ★≥30 | ★≥20 | **★≥10** |
|---|---|---|---|---|
| 24h | 2 | 3 | 4 | **9 条 ✅** |
| 72h | 9 ✅ | 18 ✅ | 24 ✅ | 32 ✅ |

- **24h 时窗必须把阈值降到 ★≥10**（才能稳拿 6 条）；若坚持 ★≥30 就必须走 72h 时窗。
- **官方博客（OpenAI/Google）只能贡献 2–3 条**（实测 OpenAI 24h 内 2 条、Google AI 24h 内 **0 条**），「官方取 4 条」的配额**结构上凑不满** → HN 顺延补齐是**主路径而非兜底**。
- 因此 AI 分组推荐实现为：**官方源（≤4，能拿几条拿几条）+ HN 聚合搜索补齐至 10 条**，并允许把「agent / model / GPU / 推理」等 AI 邻域计入（否则 24h 内只有 9 条可选，一旦有重复就掉到 6 条以下）。

## 5. 现成轮子的五个坑（我们不能重蹈）

| # | 坑 | 证据 | 我们的对策 |
|---|---|---|---|
| 1 | **无时窗过滤**，旧闻混入 | `notbrighton/ai-daily-digest` 的 `rss.py` 只 `entries[:max_per_feed]`，其 8/2 日报含 7/30 文章 | 强制 24–72h 自适应时窗，无时间戳的条目**不入日报** |
| 2 | **无去重台账** | `txk1228/daily-news-bot` 的 `shared/model.py` 只有 `class Base`，零张表 | 推送成功后写台账，双键去重 |
| 3 | **无防重入锁** | 两个轻量仓库都没有 | 文件锁 + 锁键含日期 |
| 4 | **网页解析无漂移告警** | Multiscribe 的 `article.Box-row` 匹配到 0 条时**静默返回空**，日报悄悄变瘦 | 解析条数 < 阈值即**告警并记日志**，不静默 |
| 5 | **「假成功」** | `notbrighton` 的 `main.py` 不检查 webhook 返回值，推送失败仍打印成功；飞书 HTTP 200 但 body `code != 0` | 判定 `code == 0`（HTTP 码不作为成功依据） |

## 6. 明确「不借鉴」

| 候选做法 | 不借鉴的原因 |
|---|---|
| FastAPI / SSE / 21 个路由 / CSRF / 限流 | 我们不做 Web 界面（需求 §5 非目标） |
| Postgres + Redis + Qdrant + LangChain/Haystack | 27 个依赖，与「零第三方依赖」直接冲突 |
| 自研 WorkflowEngine + 五节点 DAG + 反思循环 | 我们是一条直线流水线，DAG 只会毁掉可读性 |

## 7. 我实测验证过的关键结论（可复现）

1. **GitHub Trending 可用零依赖解析**：`re.findall(r'<article class="Box-row">(.*?)</article>', page, re.S)` + 字段正则，**13/13 条四字段全部解析成功**（repo / 描述 / 语言 / 总星 / 今日新增星）。注意：当日实际只有 **13 条**（不是固定 25），weekly 只有 11 条。
2. **RSS/Atom/RDF 三格式零依赖解析通过**：RSS2.0（OpenAI/TechCrunch/HN）、Atom（The Verge）、RDF（合成样本）全部解析成功。**踩到真 bug**：RDF/RSS 1.0 的 `title/link/description` 全在 `http://purl.org/rss/1.0/` 默认命名空间下，只用无限定名 `findtext` 会**静默返回 None**。另：`NS` 里写成 `http://purl.org/rss/`（少 `/1.0/`）也会静默失败。
3. **AI 关键词打分必须用词边界**：子串匹配 `"ai" in text` **13 个用例错 8 个**（`said`/`chair`/`domain`/`email`/`Thailand`/`chain`/`mainframe`/`available` 全误命中）；`re.search(r"\bai\b")` **错 0 个**。真实数据上，子串匹配把「BeBox is a Haiku application…」误判为 AI。
4. **飞书 A-Z-Z 缺口（最重要）**：**HN 全站热榜 + AI 关键词过滤打不满 6 条** —— 实测 front_page 30 条里只有 **3 条**命中 AI 关键词；改用 `search_by_date?query=AI|LLM|agent|OpenAI|model` 聚合，24h 内可得 **301 条**候选。**这是需求文档没写、但直接决定日报质量的关键修正。**
5. **端到端演练成功**：真实拉取 6 源 → 时窗过滤（24h：86→65 条）→ 归一化去重 → 分组配额 → **刚好凑满 20 条**。
6. **官方源结构性不足**：OpenAI 24h 内仅 2 条 / Google AI **0 条**（72h 内仅 1 条）——「官方博客取 4 条」的配额**多数日子凑不满**，HN 顺延补齐是**常态路径**而非边界情况。
7. **飞书 webhook 连通性已验证**：假 token 返回 `HTTP 200 {"code":19001,"msg":"…access token invalid"}` → 说明**必须用 body 里的 `code` 判成功**，不能看 HTTP 状态码。
8. **OSS Insight trending 端点已失效**：HTTP 200 但 `row_count=0`，`data_quality.unavailable_since=2026-03-01` → 该数据源不可用。
9. **AI 供给曲线已量化**（见 §4.5）：24h 内真 AI 条目仅 2–4 条，**必须用 `search_by_date` 多关键词聚合 + ★≥10 阈值**才能凑出 6 条。
10. **HN 官方 RSS 的摘要不可用**：其 `<description>` 内容实测为 `"Comments"` 字样，**无法作为摘要输入**，摘要只能基于标题生成（这直接影响「摘要质量」的预期）。

## 8. 飞书卡片限制：已从生产级项目定位到精确数值（来源：commit diff，非猜测）

用两个**生产项目**的修复 commit 交叉定位，取代了需求文档里模糊的「≤50」：

| 限制 | 数值 | 报错原文 / 错误码 | 来源 |
|---|---|---|---|
| **表格（table）数量** | **3 或 5（两个生产项目实测值冲突，别写死）** | `{"code":230099,"msg":"Failed to create card content, ext=ErrCode: 11310; ErrMsg: card table number over limit; ErrorValue: table;"}` | [openclaw-lark](https://github.com/larksuite/openclaw-lark)（飞书官方团队，`FEISHU_CARD_TABLE_LIMIT = 3`） vs [hermes-agent](https://github.com/NousResearch/hermes-agent/commit/a61d8102b59c8f1bbc278fe5edfe6f79187a46e9)（实测 5 张成功、6 张失败） |
| **卡片元素数量** | **200 / 卡**（**仅 card JSON 2.0**；2.0 需显式声明 `"schema":"2.0"`。官方《卡片 JSON 1.0 结构》全文无此条款，1.0 数值未证实） | `ErrCode: 11310` + `ErrMsg: element exceeds the limit` | 飞书官方文档 + hermes `_STREAM_CARD_ELEMENT_LIMIT = 180` |
| **webhook 请求体** | **20 KB 硬限（这才是我们的真实瓶颈）** | 超限被拒 | 飞书官方文档 |
| 应用发卡片请求体 | 30 KB | — | 飞书官方文档（hermes 自用阈值 28 KB） |
| 单 markdown 元素 | 3800 字符 | — | hermes 实测 |
| 卡片级限流 | 100 次/分钟、5 次/秒 | `code 230020`；另有 `11232` 限流 | openclaw `card-error.ts::isCardRateLimitError` + 飞书官方 |

**对我们（webhook 1.0 卡片，即 `msg_type=interactive`）的实际结论**：
- 我们的卡片实测 **27 个元素 / 4.7 KB**（见 §4 借鉴 4），**唯一的真实瓶颈是 20 KB 请求体上限，而不是元素数**。
- **绝不能用 markdown 表格**：20 条 = 20 张表，必撞表格上限（3 或 5）并收到 `230099 / ErrCode 11310`。用「加粗标题 + 链接 + 摘要」的列表式。
- **必须实现「超限/异常即降级为纯文本」**：openclaw 的做法是捕获 `ErrCode 11310` → 记 warn → 改发纯文本，**且不重试卡片渲染**；openclaw-lark 更进一步，**置位 `cardTableLimitHit` 让本批后续全部走纯文本**。
- **发送前必须做字节数自检**：`len(json.dumps(payload).encode("utf-8")) < 19000`，超了就**按条数截**（降条数），不要按字符硬切。

**推荐的失败处理顺序**（覆盖所有**有据可查**的错误码）：
```
19021  签名失败 / 时间戳超出 ±1 小时   → 检查签名算法（§8.1）与 timestamp 单位（秒）
19022  IP 不在白名单                   → 配置问题
19024  自定义关键词未命中              → 安全设置要求正文含关键词
11232  触发限流                        → sleep 后重试；并把计划任务挪到非整点
9499   请求体格式错误（Bad Request）    → 报文结构写错（官方原文语义：格式错误）
19001  webhook access token 无效       → 配置错误（见下方争议说明）
HTTP 200 但 code != 0                  → 一律视为失败（官方明说 StatusCode 不可信）
```

> **关于 19001 的证据争议（重要，避免误判）**：一次子调研曾提出「19001 不在官方错误码表里，它是**应用机器人权限错误**，token 失效应是 `9499 invalid hook`」。**我实测否证了这个说法**：
> - 我向 `/open-apis/bot/v2/hook/<假token>` 用**两种不同假 token**各 POST 一次，**两次都返回** `HTTP 200 {"code":19001,"msg":"param invalid: incoming webhook access token invalid"}` —— 报文自己写明 `access token invalid`。
> - 我下载官方 `add-custom-bot.md` 原文全文检索：`19001` **确实未出现**（官方只列了 19021/19022/19024 与 9499），但 `9499` 的官方语义是 **`Bad Request`（请求体格式错误）**，**不是** token 失效。
> - **结论**：`19001` 未收入官方错误码表，但**对自定义机器人 webhook 而言它就是 token 无效，且可稳定复现**。脚本按「`code != 0` 即失败并记录原文」处理最稳，**不要为单个错误码写死特殊逻辑**。

**频控**：官方原文「**单租户单机器人 100 次/分钟，5 次/秒**」+「**建议发送消息尽量避开诸如 10:00、17:30 等整点及半点时间**，否则可能出现因系统压力导致的 **11232** 限流错误」→ **计划任务设在 08:35 这类非整点时刻**。
**请求体上限**：官方原文「发送消息时，请求体的数据大小**不能超过 20 KB**」。
**安全设置**：官方原文「在同一个自定义机器人中，**你可以设置一个或多个方法**」→ **关键词 / IP 白名单 / 签名校验可叠加，不是三选一**（早期理解有误已更正）。

## 8.1 飞书加签算法：已用官方向量判定（含一个必须避免的写法错误）

两个候选实现看似矛盾，实测证明**它们其实是同一个算法**，谁都没错——一方只是对 `hmac.new` 的位置参数表述不准确。**判定依据是官方文档原文**（已下载 `add-custom-bot.md`，27729 字符），逐字如下：

> 将`timestamp + "\n" + 密钥`当做签名字符串，使用 HmacSHA256 算法**计算空字符串**的签名结果，再进行 Base64 编码。其中，`timestamp`是指距当前时间不超过 1 小时（3600 秒）的时间戳，时间单位：s。

**三个独立向量全部复算通过**（本地实算）：

| 向量来源 | timestamp | secret | 期望 sign | 结果 |
|---|---|---|---|---|
| go-lark v2.0.1 `crypto_test.go` | 1661860880 | `xxx` | `QnWVTSBe6FmQDE0bG6X0mURbI+DnvVyu1h+j5dHOjrU=` | ✅ |
| 官方示例时间戳 | 1599360473 | `demo` | `l1N0gAcBjdwBvGm1xMjOF0XSyaLRpR7tuO5dHfhAYc8=` | ✅ |
| gitea PR #34788 单测 | `1` | `a` | `rWZ84lcag1x9aBFhn1gtV4ZN+4gme3pilfQNMk86vKg=` | ✅ |

| 候选 | 写法 | 结果 |
|---|---|---|
| **A / B** ✅ | `key = f"{ts}\n{secret}"`，`msg = b""` | **命中全部向量**（两个信源实际等价） |
| C ❌ | `key = secret`，`msg = f"{ts}\n{secret}"`（网传 Java 片段常见写法） | 得 `DkEDUyVoOOJ539qBvUgMyzkzIdRWlf4e/V3Rq+ONJnQ=`，**会被判 19021** |

**为什么会产生矛盾**：Multiscribe 写的是
```python
hmac.new(string_to_sign.encode("utf-8"), digestmod=hashlib.sha256)
```
`hmac.new` 的签名是 `(key, msg=None, digestmod='')` —— **第一个位置参数就是 key**，`msg` 未传 → 默认空字节串。所以它**实际就是官方算法**；而「HMAC key 留空、secret 放在待签串里」的说法是**对 positional 参数的误读**。照误读实现（把待签串当 msg）会**签名校验失败（19021）**。

**来源与取证方式（可复用）**：官方文档虽是前端渲染页，但**自带 `.md` 纯文本镜像**，直接 GET 即可拿到含全部示例代码的原文（`https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot.md`，27729 字符）。**这是本项目最可靠的官方取证路径**，后续同类调研应优先使用。
> 注意：本会话 `web_fetch` 工具对 `open.feishu.cn` / `github.com` / `raw.githubusercontent.com` 一律报「DNS 解析到非公网 IP」而失败（本机 DNS 被代理到 `198.18.x.x`），但 **pwsh 里的 `Invoke-WebRequest` 与 `python urllib` 能正常出网** —— 全程取证走的是这条路径。

**最终实现（纯标准库，已跑通三个官方向量）**：
```python
import hmac, hashlib, base64, time

def feishu_sign(secret: str, timestamp: str | None = None) -> tuple[str, str]:
    """返回 (timestamp, sign)。timestamp 单位=秒；飞书容忍偏差 ±1 小时。"""
    ts = timestamp or str(int(time.time()))
    string_to_sign = f"{ts}\n{secret}"          # 注意：这是 HMAC 的 key，不是 message
    digest = hmac.new(string_to_sign.encode("utf-8"), b"", hashlib.sha256).digest()
    return ts, base64.b64encode(digest).decode("utf-8")
```
**要点**：① 待签串作 **key**；② message 为**空字节串**；③ timestamp **秒级**；④ `timestamp` 与 `sign` 放请求体**顶层**（`interactive` 的卡片体也在顶层 `card` 字段，不是 `content`）。
