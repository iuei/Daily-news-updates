# 飞书卡片元素上限与推送实现调研（生产级项目佐证）
> 来源：飞书官方文档 + 三个生产级项目 `larksuite/openclaw-lark`（飞书官方团队维护）、`openclaw/openclaw`、`NousResearch/hermes-agent`。每条结论附来源，推断项标「未证实」。
> 本环境 `web_fetch` 对 github.com / open.feishu.cn 报 DNS 非公网 IP，内容均由 `python urllib` 直连取得。

## 1. 元素/表格数量上限的真实数值与报错原文
**上限不是一个数字，而是多层叠加。50 是错的，无任何来源支持。**

| # | 维度 | 数值 | 适用版本 | 来源 |
|---|---|---|---|---|
| L1 | 单卡片**元素/组件总数** | **200** | **卡片 JSON 2.0** | 官方原文：「卡片 JSON 2.0 结构中，一张卡片最多支持 200 个元素（如 `tag` 为 `plain_text` 的文本元素）或组件。」[卡片 JSON 2.0 结构](https://open.feishu.cn/document/feishu-cards/card-json-v2-structure.md) |
| L2 | 单卡片 **markdown 表格数** | **5**（实测，非文档值） | CardKit 2.0 | 「limits the total number of GFM tables across the entire card… to 5… Verified empirically 2026-05-27: a single element with 6 tables fails; two elements with 4+2 tables also fail; five tables in any element layout succeed.」[hermes@7092e30](https://github.com/NousResearch/hermes-agent/commit/7092e3005046f1ce26956ae6240d915ff986472d) |
| L3 | 单卡片 **表格数**（另一实测值，**与 L2 冲突**） | **3** | CardKit 2.0 | 官方团队代码注释「4+ 张触发 230099/11310（2026-03 实测）」：`export const FEISHU_CARD_TABLE_LIMIT = 3;` [card-error.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/card-error.ts) |
| L4 | **自定义机器人 webhook 整个请求体** | **20 KB** | webhook | 「发送消息时，请求体的数据大小不能超过 20 KB。」[自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot.md) |
| L5 | **应用发卡片** 请求体 | **30 KB**（UTF-8 字节） | IM `interactive` | `_FEISHU_CARD_MAX_BYTES = 30 * 1024`；自用阈值 `_CARD_PAYLOAD_MAX_BYTES = 28000  # (official ~30 KB, we use 28 KB)` [hermes@9182dc0](https://github.com/NousResearch/hermes-agent/commit/9182dc03b552f3417e84db6715a975d9735ac06b) / [PR #63511](https://github.com/NousResearch/hermes-agent/pull/63511) |
| L6 | 单 **markdown 元素**字符数 | **3800** | CardKit 2.0 | `_CARD_MD_ELEMENT_MAX_CHARS = 3800  # Max characters per markdown element in a Card JSON 2.0 payload.` [PR #63511](https://github.com/NousResearch/hermes-agent/pull/63511) |

**超限报错原文**：外层 code `230099`（"卡片内容创建失败"，通用码，需再解子错误码），内层 `ErrCode: 11310`。
```json
{ "error": "AxiosError: Request failed with status code 400",
  "response": { "code": 230099, "msg": "Failed to create card content, ext=ErrCode: 11310; ErrMsg: card table number over limit; ErrorValue: table;" } }
```
来源：[larksuite/openclaw-lark Issue #53](https://github.com/larksuite/openclaw-lark/issues/53)。**元素总数**超限时同码不同文案：`"Failed to create card content, ext=ErrCode: 11310; ErrMsg: element exceeds the limit; code:230099"`。[card-error.ts 注释](https://github.com/larksuite/openclaw-lark/blob/main/src/card/card-error.ts)
- **关键**：`11310` 是**通用元素超限码**，源码注释明言「也覆盖模板可见性、组件上限等」——判定必须连带检查 msg 文本，不能只看 code。同源。
- 易误判形态：「同样的 errCode 230099 / 11310 也出现在直接使用 cardkit.v1.card.create API 的场景，但错误信息是 "cardid is invalid"」[Issue #53 评论](https://github.com/larksuite/openclaw-lark/issues/53)。卡 API 另有独立限流码 `230020`。[card-error.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/card-error.ts)
- 标题后缀标签 `text_tag_list` 最多 3 个（官方，[同 L1 文档](https://open.feishu.cn/document/feishu-cards/card-json-v2-structure.md)）。

**1.0 vs 2.0**：官方《[卡片 JSON 1.0 结构](https://open.feishu.cn/document/feishu-cards/card-json-structure.md)》**全文无元素数量上限条款**（已逐节核对标题与注意事项），200 只出现在 2.0 文档；1.0 上限数值**未证实**。→ 要引用 200 必须显式 `"schema": "2.0"`。L2/L3 冲突说明**表格上限不宜写死**，须做运行时兜底（见 §2）。

## 2. 超限的工程解法（逐项目）
### 2.1 `larksuite/openclaw-lark`（飞书官方团队）——预防式降级：第 4 张起表格包成代码块
不让超出的表格被识别为表格元素，前 3 张正常渲染，第 4+ 张用 ``` 包裹。
```ts
// src/card/card-error.ts
export const FEISHU_CARD_TABLE_LIMIT = 3;
export function sanitizeTextForCard(text: string, tableLimit = FEISHU_CARD_TABLE_LIMIT): string {
  // Step 1: strip fenced code blocks to avoid counting tables inside them
  // Step 2: find markdown tables outside code blocks
  if (matches.length <= tableLimit) return text;
  // Step 3: wrap excess tables in code blocks (back-to-front to preserve indices)
  for (let i = matches.length - 1; i >= tableLimit; i--) {
    const { index, length, raw } = matches[i];
    result = result.slice(0, index) + "```\n" + raw + "\n```" + result.slice(index + length);
  }
}
```
运行时报错兜底：捕获 `230099/11310` → 该 chunk 降级纯文本，**并置位后续全部走纯文本**，不再重试卡片（非表格超限错误照常 `throw`）：
```ts
// src/card/reply-dispatcher.ts
for (const chunk of chunks) {
  if (cardTableLimitHit) { await sendMessageFeishu({ ...text: chunk }); continue; } // 已降级，后续直接纯文本
  try { await sendMarkdownCardFeishu({ ...text: chunk }); }
  catch (err) {
    if (isCardTableLimitError(err)) { cardTableLimitHit = true;     // 只降级一次
      await sendMessageFeishu({ ...text: chunk }); continue; }
    throw err;
  }
}
```
发送前预检 `shouldUseCard()` 现直接返回 `false`（富文本改走 post 原生渲染），仅保留表格数守卫进入上述兜底：[reply-mode.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/reply-mode.ts)。流式卡片遇表格超限**不降级为文本，而是关掉 CardKit 流式**、保留 card_id 走终态更新；遇 `230020` **跳过该帧、不降级**：`if (isCardRateLimitError(err)) { return; }` / `if (isCardTableLimitError(err)) { this.cardKit.cardKitCardId = null; return; }`。来源：[streaming-card-controller.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/streaming-card-controller.ts)

### 2.2 `openclaw/openclaw`（社区版）——只降级为纯文本
提交信息即 `fix(feishu): degrade gracefully when card table count exceeds platform limit`。核心是 try 卡片、catch 表格超限、fallback 纯文本，并新增 `forcePlainText` 避免二次尝试卡片：
```ts
// extensions/feishu/src/outbound.ts
if (shouldRenderCard) {
  try { return await sendMarkdownCardFeishu({ cfg, to, text, accountId, replyToMessageId }); }
  catch (err) {
    if (!isCardTableLimitError(err)) throw err;   // 只处理表格超限，其余照抛
    console.warn("[feishu] card table limit hit (230099/11310), falling back to plain text");
  }
}
return sendMessageFeishu({ cfg, to, text, accountId, replyToMessageId: resolvedReplyTo,
  replyInThread: shouldReplyInThread });          // 降级：保留 thread 路由
```
错误判定兼容结构化 JSON / Axios `response.data` / 纯字符串三种形态：`const hasOuterCode = data.code === 230099; const hasInnerCode = data.errCode === 11310; const hasMsg = /table\s+number\s+over\s+limit/i.test(data.msg ?? "");` → `return (hasOuterCode && (hasInnerCode || hasMsg)) || (hasMsg && !hasOuterCode);`（后半句是「弱信号：msg 单独命中」，覆盖结构化码被丢掉的情况）。来源：[openclaw@d5b3455](https://github.com/openclaw/openclaw/commit/d5b34555c6475fc3a9fb5ff7878228eb9c0a8509)。回归佐证：[Issue #108819](https://github.com/openclaw/openclaw/issues/108819) 记录切到社区插件后丢失 `sanitizeTextForCard`/`fallback`，4+ 表格直接 HTTP 400 发不出消息。

### 2.3 `NousResearch/hermes-agent`——真分片 + 失败减半重切
```python
# PR #63511：按「字节 + 表格数」双约束装箱
def _split_elements_into_cards(elements, *, max_tables=_CARD_MAX_TABLES):
    for element in elements:
        trial_payload = json.dumps(_assemble_card(trial_elements), ensure_ascii=False)
        exceeds_bytes  = len(trial_payload.encode("utf-8")) > _CARD_PAYLOAD_MAX_BYTES
        exceeds_tables = (current_tables + elem_tables) > max_tables
        if (exceeds_bytes or exceeds_tables) and current_elements:
            cards.append(json.dumps(_assemble_card(current_elements), ensure_ascii=False))
            current_elements = [element]; current_tables = elem_tables
        else:
            current_elements = trial_elements; current_tables += elem_tables

# 收到 ErrCode 11310 后：上限减半、重切、逐张重发；任一子卡被拒则整体判失败
async def _resplit_and_send_card(self, *, payload, chat_id, reply_to, metadata):
    elements = json.loads(payload).get("body", {}).get("elements", [])
    if not elements: return None
    sub_cards = _split_elements_into_cards(elements, max_tables=max(1, _CARD_MAX_TABLES // 2))  # 5 -> 2
    for sub_payload in sub_cards:
        last_response = await self._feishu_send_with_retry(chat_id=chat_id, msg_type="interactive",
            payload=sub_payload, reply_to=reply_to, metadata=metadata)
        if not self._response_succeeded(last_response): return None   # 子卡仍被拒 → resplit 失败
    return last_response
```
两条触发路径都接：异常分支 `if msg_type == "interactive" and _CARD_TABLE_LIMIT_RE.search(error_str)`，以及**响应分支** `if not self._response_succeeded(response) and _CARD_TABLE_LIMIT_RE.search(response.msg)`；返回 `None` 才降级 `msg_type="text"` + `_strip_markdown_to_plain_text(chunk)`。流式卡片元素计数：`_STREAM_CARD_ELEMENT_LIMIT = 180`（注释：`# Feishu cards have a ~200 element limit; split before hitting it.`），达阈值即 `_split_streaming_card()` 关旧卡、`reply_to=old_msg_id` 回复开新卡。来源：[PR #63511](https://github.com/NousResearch/hermes-agent/pull/63511)、[hermes@9182dc0](https://github.com/NousResearch/hermes-agent/commit/9182dc03b552f3417e84db6715a975d9735ac06b)、[hermes@a61d810](https://github.com/NousResearch/hermes-agent/commit/a61d8102b59c8f1bbc278fe5edfe6f79187a46e9)

| larksuite/openclaw-lark | 第 4+ 张表格包代码块 + 后续全纯文本 | 否 | 是（一次性关闭卡片通道） | 预防 + 运行时捕获 |

## 3. 分片切分策略对比表
| 维度 | openclaw-lark | hermes-agent（PR #63511） |
|---|---|---|
| 切分依据 | **按字符数**（与卡片无关的通用分片） | **按 UTF-8 字节 + 表格数双约束**，另有码块边界 |
| 每片容量 | `textChunkLimit`，默认 `fallbackLimit: 4000` 字符 | 单 markdown 元素 3800 字符；单卡 28000 字节；单卡 ≤5 表 |
| 切分粒度 | 文本 chunk（不感知条目/表格） | 先按 ``` 围栏切段，再按 `\n\n` 段落装箱，超长段落按行、最后按字符硬切 |
| 片间标题 | **无**「第 N/M 部分」机制 | **无**；仅**保留最近的 `##` 标题**随表走，避免跨片丢上下文 |
| 防重复/台账 | `cardTableLimitHit` 标志位：降级后本批剩余 chunk 全走纯文本，不重试卡片 | 子卡逐张校验 `_response_succeeded`，**任一子卡失败立即返回 None**，不落成功台账；`_split_streaming_card` 失败只告警不抛出 |
| 片间顺序 | 顺序 for 循环 | 顺序 for 循环 + 多卡路径 `await asyncio.sleep(0.1)` |

出处：[reply-dispatcher.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/reply-dispatcher.ts)、[PR #63511](https://github.com/NousResearch/hermes-agent/pull/63511)、[hermes@9182dc0](https://github.com/NousResearch/hermes-agent/commit/9182dc03b552f3417e84db6715a975d9735ac06b)。
> **重要结论**：三家**都没有**实现「第 1/2 部分」这类片间标题，片间连续性全靠**回复链/线程**（`reply_to` / `replyInThread` / `thread_id`）。文字片间标题**无生产级先例可抄**。

## 4. 自定义机器人报文格式（text / post / interactive）
Endpoint：`POST https://open.feishu.cn/open-apis/bot/v2/hook/<token>`，`Content-Type: application/json`，**请求体 ≤ 20 KB**。

```json
// text（无 markdown 渲染，支持 @：<at user_id="ou_xxx">名字</at> / <at user_id="all">所有人</at>）
{ "msg_type": "text", "content": { "text": "新更新提醒" } }
// post（富文本；节点 text/a/at/img，不渲染 markdown 表格）
{ "msg_type": "post", "content": { "post": { "zh_cn": { "title": "项目更新通知",
  "content": [[ {"tag":"text","text":"项目有更新: "}, {"tag":"a","text":"请查看","href":"http://www.example.com/"} ]] } } } }
// interactive（卡片；卡片体在顶层 card，不是 content）
{ "msg_type": "interactive",
  "card": { "schema": "2.0", "config": { "update_multi": true },
    "header": { "title": { "tag": "plain_text", "content": "今日资讯" }, "template": "blue" },
    "body": { "elements": [ { "tag": "markdown", "content": "..." } ] } } }
```
来源（text/post/interactive 三例同源）：[自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot.md)。官方注意事项：「发送卡片时，需要将消息体的 `content` 字符串替换为 `card` 结构体，并对整个请求消息体进行 JSON 转义。」「通过自定义机器人发送的消息卡片，**只支持通过按钮、文字链方式跳转 URL，不支持点击后回调信息到服务端的请求回调交互**。」卡片内 @ 用 `<at id=ou_xxx></at>` / `<at id=all></at>`，仅支持 Open ID / User ID。`msg_type` 取值：`text`、`post`、`image`、`share_chat`、`interactive`（`share_user`/`audio` 等官方该页未逐一列出 → **未完全证实**）。

**成功响应（HTTP 200）**：`{ "StatusCode": 0, "StatusMessage": "success", "code": 0, "data": {}, "msg": "success" }`。官方明示 `StatusCode`/`StatusMessage` 是「冗余字段，用于兼容存量历史逻辑，**不建议使用**」——**判成功必须看 `code`**。同源。
**长度上限小结**：webhook 请求体 20 KB 是**先**触发的硬约束，它让「卡片 30 KB」实际不可用。

## 5. 加签算法：可直接用的 Python 标准库实现
**官方算法原文**：「将`timestamp + "\n" + 密钥`当做签名字符串，使用 HmacSHA256 算法计算**空字符串**的签名结果，再进行 Base64 编码。其中，`timestamp` 是指距当前时间不超过 1 小时（3600 秒）的时间戳，**时间单位：s**。例如，1599360473。」`timestamp` 与 `sign` 作为**顶层字段**与 `msg_type` 平级：`{"timestamp":"1599360473","sign":"xxx","msg_type":"text","content":{...}}`。来源：[自定义机器人使用指南 · 方式三：设置签名校验](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot.md)

```python
import base64, hashlib, hmac, time

def feishu_sign(secret: str, timestamp: int | None = None) -> tuple[str, str]:
    """返回 (timestamp_str, sign)。零第三方依赖。"""
    ts = int(time.time()) if timestamp is None else int(timestamp)  # 秒级时间戳，非毫秒
    string_to_sign = f"{ts}\n{secret}"                              # 官方：timestamp + "\n" + 密钥
    sig = hmac.new(string_to_sign.encode("utf-8"),                  # key = 签名字符串的 UTF-8 字节
                   digestmod=hashlib.sha256).digest()               # 官方：HmacSHA256
    return str(ts), base64.b64encode(sig).decode("utf-8")           # 官方：Base64 编码结果
# 用法：body = {"timestamp": ts, "sign": sign, "msg_type": "interactive", "card": card}
```

**逐行说明与坑点**
1. `timestamp` 单位**秒**（官方样例 `1599360473`），用毫秒必然失败——最常见坑。
2. 待签名内容是 `timestamp + "\n" + secret`；`\n` 是 ASCII 换行（非 `\r\n`）；`timestamp` 是**十进制字符串**（不补零、不加引号）。
3. **「计算空字符串的签名结果」= `hmac.new(key, digestmod=...)`，第二参数留默认空 `msg`**，等价 `hmac.new(key, b"", hashlib.sha256)`。**切勿把 body 或卡片 JSON 传进去**——本算法签的是空消息，不是请求体。
4. `Base64` 用标准字母表 + `=` 补齐（`base64.b64encode`），不是 urlsafe。官方 Java/Go/Python 三份示例逻辑一致。
5. **本实现已用官方向量验证**：`feishu_sign("a", 1)` → `rWZ84lcag1x9aBFhn1gtV4ZN+4gme3pilfQNMk86vKg=`，与 gitea 单测期望值逐字符相同（该测试注释标注「the result is generated by official python code」）。来源：[go-gitea/gitea PR #34788](https://github.com/go-gitea/gitea/pull/34788)
6. **容忍偏差 ±1 小时（3600 秒）**，且要求服务器时间与标准时间对齐（官方：「服务器时间与标准时间有较大偏差，导致签名过期…请校准。」）。**每次发送都重新取时间戳**，不要缓存复用。
7. 校验失败原文：`{"code": 19021, "msg": "sign match fail or timestamp is not within one hour from current time"}`。

## 6. 频控 / 重试 / 假成功处理
**频控（官方硬指标）**：「自定义机器人的频率控制和普通应用不同，为**单租户单机器人 100 次/分钟，5 次/秒**。建议发送消息尽量避开诸如 10:00、17:30 等整点及半点时间，否则可能出现因系统压力导致的 **11232 限流错误**。」[自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot.md)

**假成功（HTTP 200 但业务失败）** —— 最关键的工程点，三方都显式处理：
- 官方：`StatusCode`/`StatusMessage` 不可信，成功判据是 body 的 `code == 0`。同源。
- openclaw-lark：`if (code && code !== 0) { log.warn(...); throw new CardKitApiError({ api, code, msg, context }); }` —— 把 `code != 0` 统一升级为异常交给上层降级。[cardkit.ts](https://github.com/larksuite/openclaw-lark/blob/main/src/card/cardkit.ts)
- hermes：在 `try/except` 之外**还检查响应体**：`if msg_type == "interactive" and not self._response_succeeded(response) and _CARD_TABLE_LIMIT_RE.search(str(getattr(response, "msg", "") or ""))` —— 明确区分「抛异常」与「返回非成功响应」两条路径。[PR #63511](https://github.com/NousResearch/hermes-agent/pull/63511)
- openclaw：`assertFeishuMessageApiSuccess` 把响应断言成异常，使纯字符串错误也能被同一 predicate 捕获。[openclaw@d5b3455](https://github.com/openclaw/openclaw/commit/d5b34555c6475fc3a9fb5ff7878228eb9c0a8509)

## 7. 对我们的直接建议（Windows 计划任务 / 零第三方依赖 / 20 条 / 一张卡尽量装下）
**结论：20 条资讯用「单 markdown 元素 + schema 2.0」完全装得下一张卡，不需要分片。真正的杀手是 20 KB 请求体，不是 200 元素，也不是表格数。**
1. **用 `schema: "2.0"` + 尽量少的 markdown 元素**：20 条拼成 1 个 markdown 元素最省字节（每元素省约 30 字节 JSON 开销），且 200 元素是 2.0 专属额度（1.0 未证实有该额度）。
2. **把 20 KB 当第一硬约束，发送前自拦一道**：`len(json.dumps(body, ensure_ascii=False).encode("utf-8"))` 判断，阈值取 **19000 字节**（hermes 对 30 KB 取 28 KB，比例 0.93）。超了**按条数截**，不要按字符截（会把条目截成半句）。
3. **单 markdown 元素 ≤3800 字符**（L6）。20 条若超了，**按条数分片**（如每片 12 条）优于按字符硬切：条目边界天然是段落边界，比 hermes 的 `\n\n` 装箱更干净，且 20 KB 下通常两片足够。片间可用卡片内一行小标题（如 `第 1/2 部分`）——注意这点**三家都没做**，属自创，成本仅几字节。
4. **资讯条目默认不要用 markdown 表格**：20 条 = 20 张表，**必然撞 5 张（甚至 3 张）上限并收到 `230099 / 11310`**。用「markdown 列表 + 加粗标题 + 链接」表达。确需表格则移植 openclaw-lark 的 `sanitizeTextForCard`：**保留前 3 张，第 4 张起用 ``` 包起来**（约 20 行 Python，无依赖）。
5. **加签**：直接用 §5 的 10 行代码，**每次发送重新 `int(time.time())`**。计划任务机器若未做 NTP 同步、时钟偏移 >1 小时会稳定返回 `19021`。
6. **必须做「假成功」判定**：`urllib` 拿到 HTTP 200 不代表成功，**必须 `json.loads` 后判 `code == 0`**（`StatusCode` 不可信）。分支建议：`code == 0` → 记台账成功；`19021` → 重取时间戳重签重发一次；`11232` → `time.sleep` 后重试；`230099`（msg 含 `11310`）→ 先把表格包成代码块重发，仍失败则 `msg_type="text"` 发纯文本。**只在 `code == 0` 后才写「今日已推送」台账**，避免假成功导致漏推/重推（三家均强调逐片校验后再落账）。
7. **去重只能靠自己**：webhook 接口**无幂等键**（无 `uuid`/`dedup` 参数 → 未证实存在幂等机制）。以 `日期 + 内容哈希` 写台账文件，**所有分片全部 `code == 0` 之后**才落盘。**避开整点/半点**：官方明确建议避开 10:00、17:30 等时刻（系统压力导致 `11232`），计划任务设成 `08:35` 这类时间。
