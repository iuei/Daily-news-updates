### 可借鉴点

**A1. 配置预检返回错误列表 + `exit(1)`（`src/config.py::Config.validate`）** —— 一次列全所有配错项，而非逐个 assert；`_is_http_url`/`_parse_positive_int` 可直接抄。

```python
@classmethod
def validate(cls):
    errors = []
    if cls.LANGUAGE not in {"zh", "en"}:
        errors.append("LANGUAGE must be either 'zh' or 'en'.")
    for feed_url in cls.RSS_FEEDS:
        if not _is_http_url(feed_url):
```

**A2. 无 Key / 异常时的确定性降级（`src/summarizer/llm.py::summarize_articles`）** —— 全仓库最有价值一点：**没有 LLM 也能出报**。实证见下，76 天产出**全部**是这条路径的产物。

### 关键问题答案

**时窗过滤怎么做的？→ 完全没做。** 既非固定 24h 也非自适应：`src/fetchers/rss.py::fetch_rss_articles` 只有 `for entry in feed.entries[:max_per_feed]`（rss.py:36），**从头取 N 条，不读 `published` 做任何比较**；`published` 仅原样透传（rss.py:52 → llm.py:62）打印进日报。实锤：`digests/digest_20260802.md` 第 6/7/8 条是 NYT 7 月 30–31 日文章，混进了 8 月 2 日日报。

**LLM 摘要是批量还是逐条？失败怎么降级？长度怎么控？**
- **批量**：所有条目拼成一个 prompt，**单次** `chat.completions.create`（llm.py:70-79），无分批/逐条/并发。
- **降级**：无 key、任意异常两条路径都落 `_fallback_digest`，**无重试**。
- **长度实际不受控**：LLM 路径既无 `max_tokens` 也无截断；只有 fallback 对单条做 `_trim_text(summary, 220)`；抓取侧有 `summary[:400]`（rss.py:50）。

**webhook 报文能否直接用于飞书自定义机器人？→ 不能。** `src/notifiers/webhook.py::send_webhook_notification` 发的是 Slack/Discord 风格 `{"text":..., "content":...}`，且 `content[:2000]` 硬截断、无 `timestamp/sign`、无重试、失败只 `return False`：

```python
payload = {"text": content[:2000], "content": content[:2000]}
res = requests.post(webhook_url, json=payload, timeout=10)
if res.status_code in [200, 204]:
    return True
```

飞书要求 `{"msg_type":"text","content":{"text":...}}`；且 `main.py` 不检查返回值，推送失败照样打印 "completed successfully"。**结论：A 的 webhook 对我们无用，仅可借鉴"失败不阻断主流程"的隔离思路。**

**测试如何不联网？** 全部 `unittest`，靠 `unittest.mock.patch` 打桩 `requests.get` + 内联 XML 字节串 + 子类覆盖配置；CI 里 `python -m unittest discover -s tests` 且**未注入任何密钥**（workflow 的 `test` job 无 env）→ 证明测试路径零网络零密钥。

**日报实际条目数与摘要风格（真实文件佐证）** —— 统计全部 76 个 `digests/digest_*.md`（正则计 `^#{2,3} ` 标题数）：**75 天 = 8 条，1 天 = 7 条（`digest_20260903.md`），从未出现 20 条、也从未 ≥ 9 条**，合计 607 条。原因是默认 2 源 × `MAX_PER_FEED=4` = 8 —— 与"每天 20 条"差 2.5 倍，**这正是 A 不可直接复用之处**。摘要风格：**全为模板文本，非 LLM 生成**；最早 `digest_20260802.md` 与最新 `digest_20261016.md` 逐字对比，HN 条目一律"原始 RSS 未提供摘要，请打开链接阅读全文。"/"当前仅能确认标题和来源…"，NYT 条目一律"这条内容值得关注，建议结合原文判断其对产品、工程或行业趋势的实际影响。"——与 `llm.py::_fallback_digest` 中的字面量完全一致。**结论：76 天生产运行全程处于 fallback 模式（无有效 `OPENAI_API_KEY`），LLM 路径从未在归档中体现**；故最早 vs 最新无风格演化，结构 76 天稳定为 `### N. [标题](链接)` + `来源/时间/摘要/核心洞察` 四个 `- **x**:` 字段。

### 不足与坑

1. **无时窗过滤**（rss.py:36）→ 推旧闻，见上。
2. **无重试**：`requests.get` 单次（rss.py:25），异常只 `print` 跳过该源；webhook 同样单次。
3. **无持久化去重**：仅进程内 `seen_links`（rss.py:21），每天重跑推的几乎是同一批头条。
4. **推送失败静默**：`main.py` 不检查 `send_webhook_notification` 返回值，退出码无法反映推送状态；成功路径也无显式 `sys.exit(0)`。**`MAX_PER_FEED` 是字符串**，只在 `main.py` 里 `int()`，`Config` 不保证类型。
5. **UA 是复制粘贴残留**：rss.py:27 写的是 `AI-Daily-Digest/0.1 (+https://github.com/jieone/ai-daily-digest)`，指向 `jieone` 而非本仓库。
6. LLM 路径无 `max_tokens`，长日报会超飞书文本上限；A 用 `[:2000]` 掩盖，代价是截断正文。`index.html` 提交进仓库，Actions 提交易冲突。

### 可借鉴点

**B1. 飞书自定义机器人签名（`scripts/news_bot.py::generate_sign` / `::send_with_sign`）—— 本调研最直接可用的一段**

```python
def generate_sign(secret: str, timestamp: str) -> str:
    """生成飞书签名。"""
    key = f"{timestamp}\n{secret}"
    return base64.b64encode(hmac.new(key.encode(), b"", hashlib.sha256).digest()).decode("utf-8")


def send_with_sign(content: str) -> dict[str, Any]:
    timestamp = str(int(time.time()))
    payload = {"timestamp": timestamp, "sign": generate_sign(FEISHU_SECRET, timestamp),
               "msg_type": "text", "content": {"text": content}}
    return requests.post(FEISHU_WEBHOOK_URL, json=payload, timeout=REQUEST_TIMEOUT).json()
```

要点：**key 是 `f"{timestamp}\n{secret}"`，被签名的 message 是空字节串 `b""`**（易误写成把 body 当 message）；`timestamp/sign` 放**请求体**而非 header；成功判定是 `result.get("code") == 0`（不是 HTTP 状态码）。

**B2. 飞书排错码表（`README.md` 1.2 节，实测沉淀）**：

| 飞书返回 | 含义 | 处理 |
|---|---|---|
| `19001` access token invalid | Webhook 地址错误或仍是占位符 | 检查 Webhook URL |
| `19021` sign match fail | 签名密钥不对 / 未开签名 | 核对 Secret，确认已开启签名校验 |
| `19024` Key Words Not Found | 开了关键词但正文不含任一关键词 | 关键词加 `小可每日资讯`，或关闭关键词校验 |

**B3. RSS 重试 + 线性退避（`scripts/news_bot.py::_fetch_feed`，`FETCH_RETRIES = 2`）**

```python
def _fetch_feed(url: str, retries: int = FETCH_RETRIES) -> Any | None:
    for attempt in range(retries + 1):
        try:
            response = requests.get(url, timeout=REQUEST_TIMEOUT, headers={
                "User-Agent": USER_AGENT,
                "Accept": "application/rss+xml, application/xml, text/xml, */*"})
            response.raise_for_status()
            feed = feedparser.parse(response.content)
            if getattr(feed, "bozo", False) and not feed.entries:
                return None                      # bozo 且无 entries 才判失败
            return feed
        except Exception:
            if attempt < retries:
                time.sleep(0.6 * (attempt + 1)); continue
    return None
```

`bozo` **且无 entries** 才判失败（有 entries 的轻微格式错误仍可用），比 A 的 `print` 警告实用。

**B4. 三级源回退 + 专业源免关键词（`::search_news_by_topic`）** —— 优先级：主题专属专业源（财经→虎嗅/36氪，`keywords=None` 不强制过滤，因垂类源本身已聚焦）→ Google News 定制检索 → 通用国内 RSS（`FALLBACK_FEEDS` = IT之家/36氪/Solidot）+ 同义词过滤；每级"够数就 return"短路，共享 `seen_titles` 跨级去重。

**B5. 主题同义词表解决"标题不含主题词"（`TOPIC_SYNONYMS` + `::_match_keywords`）** —— 国内综合源标题几乎不出现"AI大模型"这种完整词，B 用同义词白名单放宽（AI大模型→ 大模型/人工智能/生成式/ChatGPT/DeepSeek/通义/文心/智谱/LLM/AIGC），`_match_keywords` 做大小写无关子串命中；配套 `_TITLE_BLOCKLIST`（"个人中心"/"的个人主页"/"登录"/"注册"…）+ `_is_junk_item` —— 这是本仓库**最接近"接地"的机制：不生成、只筛选**，从源头掐掉地方站/个人页噪声。

**B6. 三处小而实用的写法**：① `_load_feeds` 用 `_fallback_feed_cache` 避免同一 URL 被多主题重复请求，`job_news_push` 开头 `clear()` 保证幂等起点，去重键为 `item["title"].strip().lower()`；② `_load_dotenv` 零依赖手写 `.env` 解析（逐行 `partition("=")` + `strip('"').strip("'")`，`if key not in os.environ` 不覆盖已有变量）—— 我们只用标准库时可照抄，省掉 `python-dotenv`；③ `_env_int` 对 `PUSH_HOUR/PUSH_MINUTE` 非法或越界时告警并回退 07:30，不崩溃。

### 关键问题答案

**飞书推送报文与签名？** 生产路径 `scripts/news_bot.py` **只发 `msg_type: "text"`**，签名见 B1。卡片仅存在于 Coze 侧 `src/tools/feishu_message_tool.py`：`send_news_card` 用 `msg_type:"interactive"`，但 `elements[0].text.tag` 是 **`plain_text`**，把整段新闻塞成一个纯文本块（`header.title` 亦 `plain_text` + `template:"blue"`）；另有 `send_rich_text_message` 用 `msg_type:"post"`（`post.zh_cn.title` + `content:[[{"tag":"text","text":...}]]`）。**两者都不是真正的结构化卡片**（无 `lark_md`、无分栏、无链接元素），价值有限；且该文件依赖 `coze_workload_identity`，不在 CI 路径上。三处统一用 `result.get("code") == 0` 判成功。

**调度实现细节？** ①**时间点自相矛盾**：`src/tools/scheduler.py::start_scheduler` 07:30 `BackgroundScheduler`；`scripts/news_scheduler.py::main` 08:30 `BlockingScheduler` **且启动即先推一次**（`logger.info("🚀 立即执行首次推送...")` + `job_news_push()`）；`.github/workflows/daily_news.yml` cron `'30 23 * * *'` UTC = 北京 07:30（同 src 版，比 scripts 版早 1 小时）；`scripts/news_bot.py` 另有 `PUSH_HOUR=7/PUSH_MINUTE=30`；README 只说 07:30。②**防重入：无** —— 未设 `max_instances`/`coalesce`，无文件锁/无 PID 锁，`scheduler.py` 仅用全局 `_scheduler.running` 防重复 `start_scheduler`，`replace_existing=True` 只是替换同 id 任务。③**工作日判断：无** —— `CronTrigger(hour=..., minute=..., timezone="Asia/Shanghai")` **只给时分，没有 `day_of_week`**，周末照推。④`misfire_grace_time=3600`（src 版）是唯一考虑过漏触发的痕迹；本地 `--schedule` 与 GitHub Actions 同时开启会**双推**（无跨进程互斥）。

**去重/台账表结构？→ 不存在。** `src/storage/database/db.py` 只有 `get_db_url`/`_create_engine_with_retry`/`get_engine`/`get_sessionmaker`/`get_session`（`pool_size=100`、`pool_pre_ping=True`、`pool_recycle=1800`、20 秒连接重试）；`shared/model.py` **只声明 `Base`，没有任何 `Mapped`/`mapped_column` 表定义**，也无 alembic 迁移目录。业务去重**只在进程内**：`_collect_from_feeds` 的 `seen_titles: set[str]`，每次 `job_news_push` 重新开始。**→ "已推送台账"必须我们自己设计，B 提供不了表结构。**

**源抓取方式？** 三来源、统一 `feedparser`：① 专业源 RSS（`TOPIC_PRIMARY_FEEDS`：虎嗅 `rss.huxiu.com`、36氪 `36kr.com/feed`）；② Google News RSS `https://news.google.com/rss/search?q={quote_plus(query)}&hl=zh-CN&gl=CN&ceid=CN:zh-Hans`，检索词由 `TOPIC_SEARCH_QUERIES` 定制（OR 串绕开泛搜杂讯）；③ 通用国内回退 `FALLBACK_FEEDS`。`snippet` 在 `_entry_to_item` 只做 `snippet[:80]`（第 342 行）。**同样没有任何时窗过滤**，完全依赖 feed 自身排序 —— 与 A 一致。

**推送执行与状态？** `src/news_push_executor.py::execute_daily_news_push` 只是"搜 AI 新闻(3) + 搜自驾新闻(3) + `send_daily_news_func`"三行串联，返回字符串，**无状态/无重试/无幂等**；`try/except` 把异常转成 `f"每日新闻推送失败: {e}"`（吞掉退出码）。真正的状态上报在 `scripts/news_bot.py::job_news_push`：**成功返回 0、无新闻或发送失败返回 1**，由 `main()` → `sys.exit(exit_code)`。

### 不足与坑

1. **无时窗过滤**（同 A），也**无持久化去重**，跨天重复推同一批头条。
2. **`clean_snippet` 是死代码**：定义在 `scripts/news_bot.py:271-294`（含去日期/阅读量/来源标签的 10 条正则，很有用），但**全仓库无任何调用点**；实际摘要只走 `_entry_to_item` 的 `snippet[:80]`，故推送里会残留"发表于/来源：/123 阅读"。
3. **`KEYWORDS` 校验是空操作**：`format_news_content` 末尾 `_ = KEYWORDS`（第 560 行）配注释"确保关键词出现在消息中（飞书自定义机器人关键词校验）"，实际什么都没做；真正命中关键词靠硬编码标题 `🔔 小可每日资讯`。**注释与实现不符。**
4. **发送无重试**：`send_with_sign` 单次 `requests.post`，瞬时限流/5xx 直接当日失败。
5. **依赖双轨不一致**：CI 只装 3 个依赖跑 `scripts/`，`src/` 那套（coze SDK、psycopg2、boto3、opencv…）在 CI 里必然 ImportError；`src/news_push_executor.py` 还用 `from tools.news_search_tool import ...`（无 `src.` 前缀，依赖 `src` 被当作 sys.path 根）。
6. **无测试**（全仓库 0 个测试文件）、**无 LICENSE**（直接抄有合规风险）。
7. `scripts/setup_bot.py --apply-git` 会**自动改写 `.github/workflows/daily_news.yml` 的定时和主题** —— 方便但危险，CI 配置被本地脚本覆盖；`scripts/news_scheduler.py` 日志写死 `/tmp/news_scheduler.log`（Windows 不可用）且启动即推一次，与 cron 叠加会多发。
8. Google News 国内不可达（`news_bot.py:443` 只 `retries=1`、超时 15s，会白等），实际可用的是 `FALLBACK_FEEDS`。

### 关于"summary < 400 字符回退抓正文"与"事实词元接地校验"

**两仓库都不存在这两类实现**，已逐文件正则核查（`grounding|hallucin|正文|readability|trafilatura|verify|fact|校验` 全仓库无命中）：A 的 `400` 出现在 `src/fetchers/rss.py:50` 的 `"summary": summary[:400]`，是**截断上限**，不是阈值触发正文抓取；A **完全不抓文章正文**。A 对无摘要条目的处理是**留空/占位**而非补抓 —— `_fallback_digest` 输出"原始 RSS 未提供摘要，请打开链接阅读全文。"+"当前仅能确认标题和来源，后续可通过增强抓取获得更完整判断。"（正是 76 天归档中的实际文本）。B 也**不抓正文**（`_entry_to_item` 只用 `summary/description` 前 80 字符），且无模型生成内容，谈不上接地校验；B 最接近"接地"的机制是**抽取式而非生成式**（标题+来源+链接原样列出、不做评论）外加 `_TITLE_BLOCKLIST` 噪声过滤。**启示**：接地校验需我们自己实现；但 B 的"不用 LLM、只做抽取式罗列"本身就是最稳的防幻觉策略，可作"LLM 不可用/校验不通过"时的兜底形态（与 A2 合流）。

## 对我们最有价值的 5 个借鉴点（排序）

1. **B1 飞书签名（`scripts/news_bot.py::generate_sign` + `send_with_sign`）** —— 唯一可直接落地的飞书自定义机器人签名代码（key=`f"{ts}\n{secret}"`、msg=`b""`、`timestamp/sign` 入 body、`code==0` 判成功）。这是我们的目标通道，优先级最高；注意它**无重试**，我们要补指数退避。
2. **B2 飞书错误码表 + A1 配置预检** —— 19001/19021/19024 覆盖"Webhook 写错、签名没开、关键词没命中"三类必踩坑；配合 A 的"`validate()` 返回错误列表 + `exit(1)`"可在跑之前一次报清配置问题，省掉整轮调试。
3. **B4 + B5 三级源回退 + 主题同义词/黑名单（`search_news_by_topic`、`TOPIC_SYNONYMS`、`_TITLE_BLOCKLIST`）** —— 直接回应"每天凑够 20 条"的硬指标：A 只有 2 源×4 = 8 条（实证 76 天最高 8 条），B 这条链路同时兼顾条数、主题相关性与噪声控制；同义词表还解决中文源标题不含完整主题词的误杀。
4. **A5 不联网测试三件套 + workflow test job（`tests/`、`daily_digest.yml` 的 `test` job）** —— `@patch` 打桩 `requests.get` + 内联 XML、子类覆盖 `Config`、`TemporaryDirectory`；CI 无任何密钥即跑通测试。我们要交付标准库脚本，必须先有这套可离线回归的样本固定方式。
5. **A2 确定性降级 + B 抽取式排版（`llm.py::_fallback_digest` + `news_bot.py::format_news_content`/`_format_item_line`）** —— A 用 76 天真实产出证明"没有 LLM 也能稳定出报"（含 1 天仅 7 条也照常出报、不崩）；B 的 `1）标题 [来源] 🔗 链接` 紧凑排版正适配飞书 text 长度限制。两者合并 = 我们的兜底形态：LLM 不可用时退化为抽取式 20 条列表。**同时必须自补两仓库都完全没有的两块：持久化去重台账 + 时窗过滤。**

---

**结论一句话**：A 给"编排/配置预检/降级/离线测试"，B 给"飞书签名/排错码/多源回退/噪声过滤"；两者**都没有**时窗过滤、去重台账、防重入锁和接地校验 —— 这四项是我们必须自己实现的部分。
